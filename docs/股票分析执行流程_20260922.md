# 单股分析执行流程

## 1. 文档目的与范围

本文梳理 TradingAgents-CN 单股分析从前端提交、后台调度、数据准备、多智能体推理、进度更新到结果持久化的完整执行流程，并结合任务 `dd15eb75-1e6b-4dad-98a5-e01fa47141f4` 的运行日志，说明正常链路、实际执行位置、故障边界及后续验证方法。

本次实例分析对象为股票 `603345`（安井食品），任务创建于 2026-09-22 17:02:35，最终状态为 `failed`。本文只依据当前仓库源码、项目文档和本地日志作静态分析，不包含对外部模型服务的在线复测。

## 3. 总体执行架构

单股分析采用“HTTP 请求快速返回任务 ID，后台异步执行分析，前端持续读取进度和结果”的方式。核心链路如下：

```text
前端提交单股分析请求
  -> FastAPI 路由 submit_single_analysis()
  -> SimpleAnalysisService.create_analysis_task()
  -> 创建任务记录并注册 BackgroundTasks
  -> HTTP 返回任务 ID

后台任务 run_analysis_task()
  -> SimpleAnalysisService.execute_analysis_background()
  -> prepare_stock_data_async()
  -> 初始化 RedisProgressTracker
  -> _execute_analysis_sync()
  -> 提交共享线程池
  -> _run_analysis_sync()
  -> create_analysis_config()
  -> _get_trading_graph()
  -> TradingAgentsGraph.propagate()
  -> LangGraph self.graph.stream()
  -> SignalProcessor.process_signal()

正常完成
  -> 组装结构化结果和 Markdown 报告
  -> 保存结果/MongoDB 状态
  -> 更新任务状态为 COMPLETED
  -> 前端通过状态接口或 WebSocket 获取进度和结果
```

该架构包含三类状态载体：

1. 任务状态：记录 `pending`、`running`、`completed` 或 `failed` 等生命周期状态。
2. Redis 进度：记录当前步骤、步骤总数、百分比和面向前端的阶段说明。
3. 图执行状态：由 LangGraph 节点输出及回调表示智能体实际运行位置。

三者更新时间和失败处理口径并不完全一致，排障时不能只读取其中一个状态源。

## 4. 请求与后台任务生命周期

### 4.1 请求入口

`app/routers/analysis.py` 中的 `submit_single_analysis()` 接收股票代码、分析师选择、研究深度、模型配置等参数，调用 `get_simple_analysis_service()` 获取服务实例，再由 `create_analysis_task()` 创建任务。接口的职责是校验请求、持久化初始状态、注册后台执行函数并尽快向前端返回任务标识，不在 HTTP 请求线程中等待整个分析完成。

### 4.2 数据准备与进度初始化

`execute_analysis_background()` 启动后先执行异步数据准备，并按本次分析配置创建 `RedisProgressTracker`。进度步骤并非固定常量，而是根据选中的基础分析师和研究深度动态构造。

数据准备失败不一定立即终止任务。部分行情或财务数据适配器会尝试 MongoDB、AKShare、Tushare 等多个来源；若业务实现提供降级报告，流程仍可能继续进入智能体阶段，但输出质量会受影响。

### 4.3 同步核心与共享线程池

智能体图执行属于耗时同步工作。服务通过 `_execute_analysis_sync()` 将 `_run_analysis_sync()` 提交到共享线程池，避免阻塞 FastAPI 的事件循环。线程池中的核心步骤包括：

- 根据请求生成分析配置；
- 获取或创建 `TradingAgentsGraph`；
- 注册图进度回调；
- 调用 `propagate()` 执行完整智能体图；
- 处理最终信号并组装、保存报告。

线程池内部异常会向上抛回后台任务。后台任务捕获异常后将任务置为 `failed`，记录错误并注销进度跟踪器。只有 `propagate()` 正常返回后，才会进入最终信号处理、结果组装和成功持久化路径。

## 5. LangGraph 多智能体执行流程

`TradingAgentsGraph` 通过 `GraphSetup.setup_graph()` 构建节点及条件边。完整业务顺序可概括为：

```text
基础分析阶段
  所选分析师依次执行
  （如市场分析师、基本面分析师、新闻分析师、社交媒体分析师）
       |
       v
研究辩论阶段
  看涨研究员 -> 看跌研究员 -> 按研究深度循环若干轮
       |
       v
投资决策阶段
  研究经理 -> 交易员
       |
       v
风险辩论阶段
  激进风险分析师 -> 保守风险分析师 -> 中性风险分析师
       |
       v
最终裁决阶段
  风险经理 -> 信号处理 -> 报告生成
```

基础分析节点之间存在消息清理节点，例如 `Msg Clear Market`、`Msg Clear Fundamentals`。它们用于清理或整理上一节点消息，再将状态传递给下一个分析师，防止不同智能体工具消息互相污染。

### 5.1 节点日志的正确解释

`TradingAgentsGraph.propagate()` 遍历 `self.graph.stream()` 返回的 chunk。通常，一个节点完成并产生输出后，流才返回对应 chunk，随后 `propagate()` 记录节点切换并发送进度回调。因此：

- 出现“节点 A -> 节点 B”日志，通常可以证明节点 A 已完成，流程准备进入节点 B；
- 只出现节点 B 函数内部的准备日志，不能证明节点 B 已完成；
- Redis 已显示某步骤，也不能替代节点完成日志或节点输出。

这个差异是判断本次任务故障边界的关键。

## 6. 动态 20 步进度机制

`app/services/progress/tracker.py` 根据任务参数构建前端步骤。其逻辑顺序为：

1. 初始化；
2. 数据准备；
3. 每个被选中的基础分析师各占一个步骤；
4. 看涨研究员；
5. 看跌研究员；
6. 研究辩论第 1～3 轮；
7. 研究经理；
8. 交易员；
9. 激进风险评估；
10. 保守风险评估；
11. 中性风险评估；
12. 风险经理；
13. 信号处理；
14. 生成报告。

研究辩论轮数随深度变化：快速分析通常为 1 轮、标准分析为 2 轮、深度分析为 3 轮。本次任务初始化日志显示共 20 步，说明总数已经结合本次所选分析师和研究深度动态展开。

进度只能表达用户可理解的业务阶段，不能精确表示每个外部 API 请求、自动重试或节点内部子操作。因此定位卡点时，应联合使用 Redis 步骤、LangGraph 节点日志和外部客户端重试日志。

## 9. 故障边界与原因判断

### 9.1 最后成功节点与第一个失败环节

本次任务的故障边界为：

```text
基本面分析完成
  -> 基本面消息清理完成
  -> 进入看涨研究员函数
  -> 完成公司名读取和记忆查询准备
  -> 看涨研究员调用聊天补全接口
  -> 初始请求及两次自动重试均超时
  -> 异常向上传播，任务失败
```

日志没有出现 `bull_node: 发言完成`，也没有证明看涨研究员完成后的节点切换。因此应表述为“任务已进入看涨研究员，但在其内部聊天补全阶段失败”，不能表述为“看涨研究员已完成”。Redis 显示第 7 步只说明业务进度已推进到该阶段。

### 9.2 直接原因

直接原因已经由 L1 日志和 L2 源码共同确认：看涨研究员调用外部 OpenAI 兼容 `/chat/completions` 接口时，初始请求及两次自动重试均超时，最终抛出 `Request timed out.`。该异常未在智能体节点内降级处理，沿 `propagate()`、线程池和后台服务链路向上传播，导致任务进入 `failed`。

### 9.3 尚不能确定的基础根因

现有证据只能确认“外部聊天模型请求超时”，不能进一步把以下任一候选写成定论：

- 上游模型服务当时响应过慢或不可用；
- 本机到模型网关之间存在网络抖动或连接问题；
- 看涨研究员的实际上下文较长，模型处理时间超过约 60 秒；
- 当前客户端超时阈值不适合该模型和请求规模；
- 同进程其他后台任务造成资源或网络竞争。

上述候选均需通过相同 provider、model、base URL、请求上下文和 timeout 的复现实验区分。日志中基本面阶段的聊天请求曾成功返回 HTTP 200，因此不能仅根据域名相同就断言模型凭证整体失效。

## 10. 伴随问题及排除依据

### 10.1 嵌入接口 HTTP 401

日志明确显示 Qwen embedding 请求因 `InvalidApiKey` 返回 HTTP 401。这证明嵌入模型的密钥或相关端点配置异常，会使历史记忆的语义检索失效。

但 `FinancialSituationMemory.get_embedding()` 捕获嵌入异常后返回长度为 1024 的全零向量，日志也记录“记忆功能降级，返回空向量”。随后流程继续发起聊天补全请求。因此该问题是已证实的配置缺陷和质量降级项，不是本次任务直接终止原因。

### 10.2 财务数据多数据源失败

MongoDB、AKShare、Tushare 均未获得 `603345` 的完整财务指标。基本面报告生成逻辑将其记录为 warning 并继续执行，日志随后出现基本面工具返回、基本面分析完成和消息清理。因此该问题会降低基本面报告质量，但没有在本次运行中直接中断任务。

### 10.3 WebSocket 持续返回 403

从 17:02:50 起，`/api/ws/task/{id}` 多次返回 403，说明实时进度通道存在鉴权、Origin、路由依赖或连接参数问题。HTTP 状态查询仍返回 200，并最终读取到任务失败状态，证明 WebSocket 403 影响实时展示，不是智能体核心执行失败的直接原因。

### 10.4 MongoDB 后台异常

相关 MongoDB 错误出现在 17:09:34，晚于任务 17:08:23 失败，时间顺序上不能作为本次超时的原因。

### 10.5 Tushare 同步日志干扰

同一进程存在大量 Tushare 后台同步日志，但这些日志未关联本任务 ID。它们会增加检索噪声，也可能形成资源竞争候选，不过目前没有直接证据证明其导致聊天补全超时。

### 10.6 HTTP 200 的含义

状态查询接口返回 HTTP 200，只表示“查询请求成功”，不表示被查询的分析任务成功。任务是否成功必须读取响应中的业务状态或最终任务记录。

## 11. 进度状态不一致说明

本次日志同时出现：

- RedisProgressTracker 最后有效业务步骤为第 7 步“🐂 看涨研究员”；
- `memory_state_manager` 在失败更新时记录 `failed (0%)`。

这不是任务从未执行，而是两个状态源的失败更新口径不同。Redis 保留了最后已推进的业务步骤；后台失败处理调用状态管理器时没有携带已有完成百分比，导致失败状态按默认值记录为 0%。

这种不一致会误导用户和运维人员。失败状态应保留最后有效百分比、当前节点、最近完成节点、异常类别、尝试次数和失败时间，不应把已有进度覆盖为 0%。

## 13. 最小验证方案

为避免直接重跑完整任务而仍无法区分原因，建议按以下顺序验证：

1. 使用任务相同的 provider、model、base URL 和 timeout 发起最小 `/chat/completions` 健康检查，不输出密钥和完整响应正文。
2. 记录每次尝试的连接耗时、首包时间、总耗时、HTTP 状态、异常类型和客户端 attempt 编号。
3. 分别使用极短 prompt 和本任务看涨研究员的等量级上下文测试，判断超时是否与上下文长度或生成规模相关。
4. 独立校验 embedding 模型的 API Key、模型名和端点，执行最小向量请求，确认不再返回 401。
5. 重跑股票 `603345`，确认日志越过看涨研究员，至少出现 `bull_node: 发言完成` 以及其后的节点切换日志。
6. 人工构造一次可控上游超时，确认任务失败时仍保留最后业务进度、节点和重试信息。
7. 复测 `/api/ws/task/{id}`，确认浏览器侧鉴权、Origin 和路由参数正确，连接不再返回 403。

复测成功判据不应只是状态接口返回 HTTP 200，而应同时满足：图节点继续推进、Redis 进度变化、任务最终状态为 `completed`，且结果存储中存在完整分析报告。

## 14. 修复与可观测性建议

### P0：恢复核心可用性

- 对聊天模型执行同配置最小健康检查，核实 provider、model、base URL、网络连通性和约 60 秒 timeout 是否合理。
- 修复 embedding API Key、模型名或端点配置，消除 HTTP 401；密钥只通过安全配置注入，禁止写入日志或仓库。
- 若真实请求稳定超过当前阈值，基于首包和总耗时数据调整 timeout；不要在没有复测数据时单纯无限放大超时。

### P1：改进失败定位和用户反馈

- 外部模型调用日志增加 provider、model、脱敏 base URL、timeout、attempt、耗时和异常类型，不记录 API Key、完整 prompt 或完整响应。
- 为上游超时、鉴权失败、限流、模型不存在和业务代码错误设置不同错误码，前端展示可操作的失败原因。
- 失败更新保留最后进度、最近成功节点和当前节点，避免出现“第 7 步”和“failed 0%”冲突。
- 根据幂等性明确可重试异常范围；在节点级记录重试，而不是只留下通用 `Request timed out.`。
- 排查 WebSocket 的鉴权、Origin、代理转发和路由依赖，恢复实时进度能力。

### P2：降低质量风险和日志噪声

- 财务数据全部缺失时，在报告和前端明确标记降级来源、缺失字段及对结论可信度的影响。
- 将 Tushare 批量同步与单股分析日志分流，并统一携带 task ID、trace ID 或 job ID，减少跨任务污染。
- 为单股任务补充结构化阶段耗时，便于快速识别数据源、模型调用或持久化瓶颈。
- 更新 Understand 图谱，使后续架构定位与当前源码一致。

## 15. 排障检索模板

定位单个任务时，建议先以任务 ID 建立主时间窗，再补充异常、节点和 Trace ID 检索：

```powershell
rg -n --fixed-strings "dd15eb75-1e6b-4dad-98a5-e01fa47141f4" logs
rg -n "Request timed out|Retrying request|InvalidApiKey|WebSocket.*403" logs
rg -n "Bull Researcher|bull_node|Fundamentals Analyst|Msg Clear Fundamentals" logs/tradingagents.log*
rg -n --fixed-strings "85d47231-b075-4d6e-b18e-2a317939d729" logs
```

推荐按以下顺序输出排障结论：

1. 用户现象和业务影响；
2. 任务基本信息与时间窗；
3. 最后成功节点；
4. 第一个失败节点或外部调用；
5. 直接异常及重试情况；
6. 已证实直接原因；
7. 待验证基础根因；
8. 伴随问题及排除依据；
9. 最小验证步骤和成功判据。

## 16. 结论

任务 `dd15eb75-1e6b-4dad-98a5-e01fa47141f4` 已完成请求创建、数据准备、市场分析和基本面分析，并进入看涨研究员阶段。看涨研究员完成公司信息和记忆查询准备后，其 `/chat/completions` 请求连续三次约 60 秒未成功返回，最终以 `Request timed out.` 终止。任务没有进入看跌研究员、研究经理、交易员、风险评估、信号处理和正常报告持久化阶段。

嵌入接口 HTTP 401、财务数据缺失和 WebSocket 403 都是真实存在的问题，但源码和时间线表明它们分别属于记忆能力降级、数据质量降级和实时展示故障，不是本次任务直接中断原因。当前最准确的根因表述是“外部聊天模型请求超时”；具体是上游服务、网络、上下文规模还是 timeout 配置导致，仍需按最小验证方案复测。
