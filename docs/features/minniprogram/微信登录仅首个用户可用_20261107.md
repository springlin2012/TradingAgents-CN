# 微信登录仅首个用户可用

> 日期：2026-11-07
> 现象：同一个小程序，**开发者本人的微信可以登录，其他用户点「微信一键登录」都失败**。
> 排查范围：`niunai-analysis-tools`（小程序）+ `TradingAgents-CN`（FastAPI 后端）。
> 结论：**后端微信新用户自动注册存在数据库唯一键冲突，第一个微信用户建号成功后，后续所有未返回 unionid 的用户都无法建号**，前端只提示「微信登录失败」。
>
> 修复状态（2026-11-09）：后端已按第五节落地。`get_or_create_wechat_user()` 在 unionid 为空时不再写入该字段；`wechat_unionid` 改为 `$type:string` 部分唯一索引；`DuplicateKeyError` 时打日志、按 username 回查。存量 `wechat_unionid=null` **不由系统自动清理**，需人工按第三节脚本处理。部署后需重启 FastAPI。线上库仍建议先做第六节只读确认。

---

## 一、问题结论

| 项目 | 内容 |
| --- | --- |
| 现象与影响 | 仅首个微信账号可登录；此后所有新微信用户登录失败（401）。密码登录、手机号登录不受影响。 |
| 故障边界 | 最后成功节点：`jscode2session` 换到 openid → 第一个失败节点：`users` 集合 `insert_one` 抛 `DuplicateKeyError` |
| 直接原因 | `get_or_create_wechat_user()` 插入新用户时被 `wechat_unionid_1` 唯一索引拒绝，异常兜底又查不到该用户，最终返回 `None`，路由抛 401「微信登录失败」 |
| 根因 | `wechat_unionid` 建的是 **unique + sparse** 索引，但代码把 `unionid=None` **显式写进文档**。MongoDB 的 sparse 只跳过「字段缺失」，不跳过「字段存在且值为 null」；null 也占唯一索引槽位 |
| 证据等级 | 代码缺陷：**已证实**（源码 + 隔离库复现）；线上已触发该路径：**高概率**（见第六节证据缺口） |
| 触发条件 | 小程序未绑定微信开放平台 → `jscode2session` 不返回 `unionid`；且库里已有第一个写入 `wechat_unionid: null` 的微信用户 |
| 伴随问题 | 本地 `.env` 缺微信配置项（不影响当前线上）；异常被静默吞掉，无日志；错误文案不区分失败阶段 |

**为什么恰好是「我的能登录、别人不行」**：第一个用微信登录的人（开发者本人）成功插入了 `wechat_unionid: null`；此后每个新用户的 openid 虽然各不相同，但 `wechat_unionid` 都是 null，全部撞在同一条唯一索引上。手机号用户和旧账号文档里**没有** `wechat_unionid` 字段，被 sparse 跳过，所以其他登录方式正常。

## 三、证据与判断

| 证据位置 | 事实 | 支持的结论 |
| --- | --- | --- |
| `TradingAgents-CN/app/services/user_service.py:42-44` | `create_index("wechat_unionid", unique=True, sparse=True)`，服务启动即建 | 唯一索引一定存在（创建失败仅 warning 忽略） |
| `user_service.py:307-314` | 新用户文档显式带 `wechat_unionid=unionid`，无 unionid 时值为 `None` | null 被写入，sparse 不跳过 |
| `user_service.py:320-324` | `except DuplicateKeyError` 中按 openid 重查，查不到则返回 `None` | 冲突后静默失败，不抛可诊断错误 |
| `auth_db.py:245-250` | 拿到 `None` 后抛 401「微信登录失败」 | 前端看到的最终文案 |
| 隔离库复现（本机 MongoDB 实测） | 建同款索引后：第 1 条 `unionid=None` 插入 OK；第 2 条报 `DuplicateKeyError E11000`；字段完全缺失的第 3 条插入 OK | **直接证实缺陷成立**，且解释「只有微信登录受影响」 |
| 线上探测 `curl --noproxy '*' POST https://www.niunai.online/api/auth/login` | 微信分支无效 code 返回 `401 {"detail":"微信登录失败，请重试"}`；密码分支返回 `401 {"detail":"用户名或密码错误"}` | TLS/SNI 已恢复、后端已配 AppId/Secret（否则 503）、路由正常 → 排除网络层与配置缺失作为当前阻碍 |

- **appid 不匹配**：`wechat_auth_service.py:28-30` 对所有用户用同一运行时 appid，不区分账号。
- **HTTPS 握手失败**：`docs/analysis/登录接口HTTPS握手失败_20261028.md` 记录的问题当前已恢复（实测域名直连返回业务 401，不是连接重置）。
- **完善资料页未注册**：`app.json` 已注册 `loginProfile` 分包，`goFillProfileIfNeeded` 跳转链路完整。
- **后端白名单 / 内测名单**：全库扫描 `app/` 无用户准入白名单逻辑。
- **登录按钮未绑定**：`pages/login/login.wxml:27` 已绑 `bindtap="onWechatLogin"`，默认 `loginMode: 'wechat'`。

## 五、修复方向

### 1. 代码修复（后端，最小改动，推荐）

`app/services/user_service.py` `get_or_create_wechat_user()`：**unionid 为空时不要写这个字段**，让 sparse 索引真正生效。

```python
fields = dict(
    username=username,
    email=f"{openid}@wechat.local",
    wechat_openid=openid,
    is_verified=True,
)
if unionid:
    fields["wechat_unionid"] = unionid
user_doc = self._new_user_doc(**fields)
```

 或者从数据层加固（二选一或同时做）：把索引换成 partial index，只索引真实字符串值，需先 `drop_index("wechat_unionid_1")`：

```python
self.users_collection.create_index(
    "wechat_unionid",
    unique=True,
    partialFilterExpression={"wechat_unionid": {"$type": "string"}},
)
```

### 2. 异常兜底与可观测性

`get_or_create_wechat_user()` 的 `except DuplicateKeyError` 现在会静默返回 `None`。至少补上日志（openid 只打前 8 位，不落全文），并在兜底重查失败时按 `username` 再查一次；否则同类问题依旧无法从日志定位。

### 3. 存量数据清理（线上库，人工执行，执行前先备份）

系统启动**不会**自动 `$unset` 存量 null。代码上线后由人工把历史写入的 null 字段抹掉：

```js
db.users.updateMany(
  { wechat_unionid: { $type: "null" } },
  { $unset: { wechat_unionid: "" } }
)
```

### 4. 本地开发配置

本地 `.env` 共 173 个键，**没有** `WECHAT_MINI_APPID` / `WECHAT_MINI_SECRET`（仅 `.env.backup` 与 `.env.example` 有）。本地起服务时微信登录会返回 503。请从备份补回这两项（不要提交进版本库）；线上已配置，无需改动。

## 六、证据缺口

- 本次连接的 MongoDB（`192.168.66.81`，库 `tradingagentscn_v0_..._linshi`）`users` 集合为空，判定为开发/临时库，**不是线上生产库**，因此无法直接确认线上那条 `wechat_unionid: null` 文档是否已存在。需在线上库执行只读查询确认：

```js
db.users.getIndexes()                                    // 看 wechat_unionid_1 是否 unique+sparse
db.users.countDocuments({ wechat_unionid: { $type: "null" } })
db.users.countDocuments({ wechat_openid: { $exists: true } })  // 预期：恰好 1（首个登录者）
```

- 无法从仓库确认小程序**发布状态与体验成员名单**，以及 mp 后台「服务器域名 → request 合法域名」是否登记 `https://www.niunai.online`。开发者工具 `urlCheck: false` 会跳过域名校验，**体验版 / 正式版不会跳过**。若其他用户用的是非调试模式且域名未登记，会走 `wx.request` fail（文案见第四节末行），属于并列的另一道阻碍。

## 七、验证与回归

1. 修复前，在线上库执行第六节三条只读查询，确认「微信用户数 = 1 且存在 null 文档」。
2. 部署代码修复 + **人工执行第三节存量清理** + **重启 FastAPI**。

4. 回归：密码登录、手机号验证码登录、老微信用户再次登录（应命中 existing 分支）、退出后重登。
5. 确认失败文案：无效 code 仍为「微信登录失败，请重试」，不再出现无「请重试」的「微信登录失败」。
6. 若其他用户仍失败，按第四节文案分流；若出现「网络异常…」，转查 mp 后台 request 合法域名与服务器域名配置。
