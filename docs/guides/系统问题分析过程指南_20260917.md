# 系统问题分析过程指南

> 适用对象：负责分析系统异常的 Agent
>
> 目标：用最少检索快速定位故障边界，形成可验证、可复现的结论。

## 一、最终必须回答的问题

分析结束时，必须明确回答：

1. **现象与影响**：用户看到什么，哪些功能、任务或数据受到影响。
2. **故障边界**：最后成功节点和第一个失败节点分别是什么。
3. **直接原因**：哪一个异常实际中断了本次调用链。
4. **根因与证据等级**：为什么发生该异常，证据是否充分。
5. **触发条件与伴随问题**：什么条件触发了故障，哪些异常只是同时出现。
6. **验证与修复步骤**：如何用最小操作验证判断，并确认问题已解决。

页面上的“分析过程中发生错误”“请检查参数或稍后重试”等通用提示，只是现象，不是根因。

## 二、快速分析流程

### 第 0 步：加载规则和历史经验

开始分析前：

1. 读取项目根目录的 `AGENTS.md`、`CLAUDE.md`。
2. 阅读项目问题解决指南、知识库索引及相关历史记录。
3. 了解日志位置、服务边界、配置来源和关键调用链。

若项目已提供知识图谱，先用图谱定位模块和依赖，再以源码、日志和实际配置核对结论。

#### 本项目常用日志入口

| 日志文件 | 主要用途 | 优先检索内容 |
| --- | --- | --- |
| [`error.log`](../../error.log) | 定位最终异常、Redis 错误及数据源异常 | 异常类型、完整堆栈、错误时间、任务 ID、Trace ID |
| [`tradingagents.log`](../../logs/tradingagents.log) | 还原市场分析师节点、模型调用及网关 HTTP 200 响应的完整执行链路 | 节点开始/完成、模型请求与响应、业务结果、重试和降级 |
| [`webapi.log`](../../logs/webapi.log) | 确认请求参数、任务 ID、Trace ID、后台任务状态及状态查询结果 | 请求入口、参数摘要、关联标识、任务创建/执行/完成状态 |

只有页面通用错误提示时，推荐按以下顺序检索：

1. 在 `webapi.log` 中按时间和请求入口锁定任务 ID、Trace ID 与请求参数；
2. 使用关联标识在 `tradingagents.log` 中还原完整执行链路，找出最后成功节点和第一个失败节点；
3. 在 `error.log` 中确认最终异常、完整堆栈及 Redis、数据源等底层错误；
4. 按时间、任务 ID 和 Trace ID 交叉核对三份日志，避免把不同请求的异常错误关联。

若已掌握明确异常时间或异常关键字，可先从 `error.log` 定位，再反向关联另外两份日志。日志中的 HTTP 200 仅表示网关请求成功，仍需检查业务结果和后台任务最终状态。

### 第 1 步：锁定本次故障

优先收集以下标识，避免把不同请求的日志混在一起：

- 任务 ID、请求 ID、Trace ID、用户或业务主键；
- 故障发生时间和时区；
- 环境、服务、实例或 Pod；
- 请求入口、关键参数和操作步骤；
- 是否稳定复现，以及最近一次成功时间。

如果缺少唯一标识，至少使用“时间窗口 + 入口 + 业务对象”缩小范围。检索窗口先小后大，避免一开始读取全部日志。

### 第 2 步：还原最短有效时间线

围绕同一请求，按时间排序保留关键节点：

```text
请求进入 → 参数校验 → 配置/数据加载 → 核心处理 → 外部调用 → 结果保存 → 状态回写 → 响应返回
```

重点记录：

- 每个节点是否开始、成功、失败或超时；
- 第一条异常及其完整堆栈；
- 异常前最后一条成功日志；
- 正常流程应出现但实际缺失的完成日志；
- 重试、降级、回退和异常转换行为。

不要仅凭最早出现的告警下结论。早期告警可能已被降级处理，真正中断流程的异常通常出现在后续节点。

### 第 3 步：确定故障边界

用一句话描述边界：

```text
最后成功节点 → 第一个失败节点
```

判断时同时检查：

- 上游是否已成功生成有效输入；
- 当前节点是否真正开始执行；
- 下游完成日志或状态更新是否缺失；
- HTTP、队列或进程层面成功，是否掩盖业务失败。

注意：HTTP 200、消息消费成功或进程未退出，并不等于业务处理成功。应继续检查业务状态码、结果字段、任务状态和持久化结果。

### 第 4 步：从异常反查实现

以“异常类型 + 报错方法 + 关键字段”为入口，依次确认：

1. 异常在哪一行、哪个方法抛出或重新包装；
2. 该方法的调用方、输入来源和正常输出；
3. 失败字段是否可能为空、缺失、类型不符或结构变化；
4. 相关配置从哪里读取，实际生效值是什么；
5. 外部接口、数据库、缓存、队列或模型返回了什么；
6. 最近代码、配置、依赖、数据源或部署是否发生变化。

判断运行状态时，以实际证据为准：

- 配置文件表示期望值，运行日志和配置中心表示实际生效值；
- 依赖清单或锁文件表示期望版本，实际安装版本和启动日志表示运行版本；
- 源码定义表示预期行为，部署镜像、提交号和运行堆栈表示线上行为。

### 第 5 步：分类并验证原因

先分类，避免把所有异常都写成“根因”：

| 类型 | 判断标准 |
| --- | --- |
| 直接原因 | 实际中断本次调用链的异常 |
| 根因 | 有证据解释直接异常为何发生 |
| 触发条件 | 使流程进入故障路径的输入、配置、切换或环境差异 |
| 伴随问题 | 同时出现，但流程继续或不在最终异常链上 |

每项判断标记证据等级：

| 等级 | 含义 |
| --- | --- |
| 已证实 | 日志、源码、配置或复现结果直接证明 |
| 高概率 | 多项证据一致，但缺少关键输入、响应或堆栈 |
| 待验证 | 目前只有可能性，没有直接证据 |

验证时遵循单变量原则：一次只调整一个输入、配置、依赖或环境条件，然后重复同一请求并比较结果。优先选择可回滚、影响最小的验证方式。

### 第 6 步：输出结论

使用事实和证据描述，不使用“可能是配置问题”“建议重试”等空泛结论。证据不足时，应明确写出“当前可确认结论 + 证据缺口 + 下一步验证”，不得把推测写成事实。

推荐模板：

```markdown
## 问题结论
- 现象与影响：
- 故障边界：最后成功节点 → 第一个失败节点
- 直接原因：
- 根因及证据等级：已证实 / 高概率 / 待验证
- 触发条件：
- 伴随问题：

## 关键时间线
| 时间 | 组件/方法 | 事件 | 结果 | 证据位置 |
| --- | --- | --- | --- | --- |

## 证据与判断
| 证据位置 | 事实 | 支持的结论 |
| --- | --- | --- |

## 证据缺口
- 缺少什么：
- 因此不能确认什么：

## 建议
1. 最小验证步骤：
2. 修复方向：
3. 回归检查：
```

## 三、常见问题的定位入口

| 现象 | 优先检查 |
| --- | --- |
| 参数校验失败 | 必填项、格式、枚举值、长度、时间范围、前后端字段映射 |
| 空值、字段或类型异常 | 上游原始数据、序列化结果、接口结构变化、默认值和兼容逻辑 |
| 外部接口失败 | 请求参数、认证、状态码、业务码、响应体、限流、超时和重试 |
| 数据过期或缺失 | 数据日期、市场/业务日历、缓存时间、数据源更新时间和降级来源 |
| 配置未生效 | 配置优先级、环境变量、配置中心、实例差异、重启或热加载情况 |
| 依赖或环境差异 | 实际安装版本、运行时版本、镜像标签、提交号和启动日志 |
| 异步任务状态异常 | 入队、消费、执行、结果保存、状态回写和超时回收 |
| 页面显示通用错误 | 后端业务响应、任务详情、服务日志和原始异常堆栈 |

## 四、Agent 分析约束

1. **先证据，后结论**：所有关键判断必须能指向日志、源码、配置、数据或复现结果。
2. **先边界，后扩展**：先找到最后成功节点和第一个失败节点，再调查更早的告警。
3. **区分事实与推测**：未验证内容必须标记证据等级和验证方法。
4. **控制检索范围**：先按请求标识和小时间窗检索，再按调用链扩大范围。
5. **保留原始异常**：优先记录异常类型、消息、堆栈、组件、时间和关联标识。
6. **检查缺失事件**：正常应出现但缺失的日志或状态，常用于确认流程停止位置。
7. **不被表面成功误导**：同时核对传输状态、业务状态和最终数据状态。
8. **不泄露敏感信息**：不得在报告中暴露 API Key、Token、Cookie、认证头、隐私数据或完整敏感响应。
9. **不把重试当修复**：重试只能用于判断偶发性，不能替代根因分析。
10. **修复后验证闭环**：重复原始场景，并检查结果、状态、日志和相关回归场景。

## 五、完成检查清单

- [ ] 已锁定同一请求、任务或业务对象；
- [ ] 已给出最后成功节点和第一个失败节点；
- [ ] 已找到真正中断流程的异常；
- [ ] 已区分直接原因、根因、触发条件和伴随问题；
- [ ] 每项关键结论都有证据位置和证据等级；
- [ ] 已说明证据缺口，没有把推测写成事实；
- [ ] 已提供最小验证步骤、修复方向和回归检查；
- [ ] 报告中没有敏感信息；
- [ ] 修复后已验证原始场景和最终业务状态。
