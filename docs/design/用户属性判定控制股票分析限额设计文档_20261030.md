# 用户属性判定控制股票分析限额设计文档

> 文档日期：2026-10-30  
> 文档状态：待实施  
> 适用范围：股票分析提交入口、用户额度管理、分析任务结算

## 1. 背景与结论

系统已经在 `users` 集合中保留 `daily_quota` 字段，但该字段尚未参与分析任务的准入和结算。本设计复用该历史字段，将它定义为每个用户每天可占用的股票分析数量上限，并补齐并发控制、批量扣减、任务失败释放、幂等重试和跨日结算。

当前代码结论如下。

| 对象 | 当前作用 | 当前是否参与额度控制 |
| --- | --- | --- |
| `user_tags` 集合 | 保存用户自定义的自选股分类标签，包括名称、颜色和排序 | 否 |
| `users.daily_quota` | 保存并向前端展示用户日额度；普通用户初始化为 `1000`，默认管理员初始化为 `10000` | 否 |
| `QuotaMiddleware` | 设计为通过 Redis 按请求计数，但使用固定额度 `1000` | 否，当前未在 `app/main.py` 挂载 |

因此，`user_tags` 不承担用户角色、权益或额度分组功能。修改、删除或新增自选股标签不得改变用户额度。`users.daily_quota` 是本设计中唯一的用户日额度来源。

## 2. 目标与边界

### 2.1 目标

- 让 `users.daily_quota` 对所有股票分析提交入口实际生效。
- 单股与批量分析按股票数量使用同一个日额度。
- 在并发请求下保证实际占用量不超过用户额度。
- 同一次提交重试不重复占用额度。
- 任务成功后确认消耗，最终失败或取消后释放预占。
- 提供用户额度查询和管理员额度修改能力。
- 保留普通用户 `1000`、管理员 `10000` 的历史初始化语义。

### 2.2 非目标

- 不使用 `user_tags` 表达用户身份或额度等级。
- 不把现有 `concurrent_limit` 合并到日额度中。并发任务数和每日分析数是两种独立限制。
- 不对行情查询、报告查看、自选股维护和股票筛选结果查询计费。
- 不在本设计中改变分析模型、任务优先级或计费规则。

## 3. 当前实现分析

### 3.1 `user_tags` 的作用和场景

`app/services/tags_service.py` 使用 MongoDB `user_tags` 集合保存用户自定义标签。主要字段如下：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 标签所属用户 |
| `name` | 标签名称 |
| `color` | 前端展示颜色 |
| `sort_order` | 标签排序值 |
| `created_at`、`updated_at` | 创建和更新时间 |

集合通过 `(user_id, name)` 唯一索引防止同一用户创建重名标签，并通过 `(user_id, sort_order)` 索引支持排序。`app/routers/tags.py` 的增删改查均使用当前认证用户的 `user_id`。前端自选股页面使用这些标签进行分类、颜色展示和筛选。

这是一套个人数据分类功能，与账号角色、分析权益和每日额度没有业务关联。

### 3.2 `users.daily_quota` 的历史语义

`app/models/user.py` 将 `daily_quota` 定义为整数，默认值为 `1000`。普通用户创建时写入 `1000`，默认管理员创建时写入 `10000`。用户响应、管理员用户列表和前端认证状态会返回或展示该字段。

字段目前存在以下缺口：

- 分析提交前没有读取该字段。
- 任务创建、执行成功或失败时没有更新用户额度账本。
- 字段缺少非负数校验。
- 普通用户和管理员均没有完整、受控的额度修改闭环。

### 3.3 旧中间件不能直接满足需求

`app/middleware/rate_limit.py` 中的 `QuotaMiddleware` 不能作为本功能的实现基础，原因如下：

- 中间件使用构造参数中的固定 `daily_quota=1000`，不读取 `users.daily_quota`。
- 它按 HTTP 请求次数计数，批量分析只会计为一次。
- Redis 自增发生在业务参数规范化和任务创建之前，无法准确处理无效请求和失败释放。
- Redis 异常时直接放行，可能突破额度。
- 它只列出了部分接口，无法确保四个分析提交入口共享同一规则。
- `app/main.py` 当前没有挂载该中间件。

旧中间件可以继续承担请求频率限制，但不能作为权威日额度账本。

## 4. 额度规则

### 4.1 权威额度

`users.daily_quota` 表示用户每天允许占用的股票分析数量：

- `0`：禁止提交新的股票分析。
- 正整数：当天最多占用对应数量的股票分析。
- 普通用户历史默认值：`1000`。
- 管理员历史默认值：`10000`。
- 管理员同样受自己 `daily_quota` 字段约束。

字段必须是非负整数。上线前迁移所有缺失值；运行时如果发现字段缺失、类型错误或值为负数，准入服务返回 `503 Service Unavailable` 并记录告警，不使用前端默认值，也不静默放大额度。

### 4.2 消耗单位

- 每个规范化后的唯一股票标的消耗 `1` 个额度。
- 单股分析的 `cost` 为 `1`。
- 批量分析的 `cost` 为市场和股票代码规范化、去重后的标的数量。
- A 股、港股和美股共用同一个用户日额度。不同市场中的相同代码视为不同标的。
- 批量提交必须一次性预占全部 `cost`。余额不足时整批拒绝，不接受部分股票。
- 参数校验失败、重复幂等请求、查询行情、查看历史报告和维护自选股不消耗额度。

### 4.3 业务日

业务日按服务配置的 `Asia/Shanghai` 时区计算，格式为 `YYYY-MM-DD`。任务始终归属于首次成功预占时的业务日，即使任务跨过午夜才完成，也在原业务日账本中结算。

## 5. 数据设计

新增 MongoDB 集合 `analysis_quota_daily`，作为权威每日额度账本。每个用户每天只有一条文档。

```json
{
  "_id": "ObjectId",
  "user_id": "用户ID",
  "business_date": "2026-10-30",
  "reserved": 2,
  "succeeded": 5,
  "released": 1,
  "last_applied_limit": 1000,
  "entries": {
    "幂等键哈希生成的安全提交ID": {
      "idempotency_key_hash": "客户端幂等键的SHA-256摘要",
      "request_hash": "规范化请求摘要",
      "cost": 2,
      "reserved": 2,
      "succeeded": 0,
      "released": 0,
      "quota_snapshot": 1000,
      "status": "reserved",
      "task_ids": ["固定任务ID-1", "固定任务ID-2"],
      "created_at": "ISODate",
      "updated_at": "ISODate"
    }
  },
  "created_at": "ISODate",
  "updated_at": "ISODate"
}
```

计算规则：

```text
occupied = reserved + succeeded
remaining = max(current_daily_quota - occupied, 0)
```

索引要求：

```javascript
db.analysis_quota_daily.createIndex(
  { user_id: 1, business_date: 1 },
  { unique: true, name: "uk_user_business_date" }
)
```

`entries` 保存提交意图和结算状态，既用于幂等，也用于预占后任务尚未持久化时的恢复。单次批量提交对应一个 entry，其中每个股票对应固定任务 ID；部分成功时可以按任务逐项结算。若后续允许极高的单日提交量，应将 entry 拆分到独立集合，并使用 MongoDB 事务维护计数一致性，避免单文档接近 MongoDB 16 MB 上限。

分析任务文档增加以下额度关联字段：

```json
{
  "quota_submission_id": "01J...提交ID",
  "quota_business_date": "2026-10-30",
  "quota_cost": 1
}
```

## 6. 统一准入流程

以下四个入口必须调用同一个 `AnalysisQuotaService.reserve()`，路由层不得自行扣减：

- `POST /api/analysis/single`
- `POST /api/analysis/batch`
- `POST /api/analysis/analyze`
- `POST /api/analysis/analyze/batch`

准入顺序如下：

1. 从认证上下文获取 `user_id`，校验用户和账号状态。
2. 校验请求参数，规范化市场和股票代码，并对批量标的去重。
3. 读取 `users.daily_quota`，校验它是非负整数。
4. 读取调用方提供的 `Idempotency-Key`。前端必须在发起请求前生成 UUID，并在未知结果重试时复用；缺失或格式非法时返回 `400 Bad Request`。服务端不保存原始键，而是计算 SHA-256 摘要，并由摘要生成可安全用于 MongoDB 字段名的固定提交 ID。
5. 使用规范化请求生成 `request_hash`。同一用户、业务日和幂等键必须对应相同摘要，否则返回 `409 Conflict`。幂等范围为“用户 + 业务日”，客户端每天为新提交生成新键。
6. 服务端为批量中的每个股票预先生成固定任务 ID，并将任务 ID写入提交 entry。
7. 在 `analysis_quota_daily` 单文档上执行条件更新，只有满足 `reserved + succeeded + cost <= daily_quota` 时才原子增加 `reserved` 并写入 entry。
8. 预占成功后，使用固定任务 ID 持久化任务并投递队列。
9. 返回任务 ID、额度占用和剩余额度。

额度不足时返回 `429 Too Many Requests`，响应示例：

```json
{
  "detail": {
    "code": "DAILY_QUOTA_EXCEEDED",
    "limit": 1000,
    "occupied": 1000,
    "remaining": 0,
    "requested": 3,
    "business_date": "2026-10-30",
    "resets_at": "2026-10-31T00:00:00+08:00"
  }
}
```

同一幂等键和相同请求重试时，服务返回原提交结果，不再次增加 `reserved`。MongoDB 写入发生超时且服务无法确认结果时返回 `503 Service Unavailable`，客户端使用原幂等键重试，服务通过 entry 判断预占是否已经完成。所有官方前端和内部调用方都必须持久保留进行中请求的幂等键，直至获得确定响应。

## 7. 任务创建一致性与恢复

当前 `create_analysis_task` 在 MongoDB 持久化失败后仍可能返回成功。接入额度后必须调整为“任务持久化成功才表示创建成功”，并允许调用方传入预生成的固定任务 ID。

预占和任务文档写入之间存在短暂窗口。为避免孤儿预占，采用可恢复的提交意图：

- 额度 entry 先记录固定任务 ID 和规范化请求摘要。
- 任务写入使用固定任务 ID，重复写入必须幂等。
- 投递队列前更新任务状态，重复投递由任务 ID 去重。
- 恢复任务定期扫描长时间处于 `reserved` 且缺少任务文档的 entry。
- 能根据 entry 恢复创建时，继续创建和投递原任务。
- 已确认无法恢复且从未进入执行阶段时，执行幂等释放。
- 状态未知时继续保留预占并告警，不能直接放行额度。

如果部署环境已启用 MongoDB 副本集，可将用户额度读取、原子预占和任务持久化放入事务，进一步缩短恢复窗口；恢复任务仍需保留以处理队列投递失败。

## 8. 任务结算

任务状态进入终态时调用 `AnalysisQuotaService.settle()`：

| 任务结果 | 账本变化 | 说明 |
| --- | --- | --- |
| 成功 | `reserved -= 1`，`succeeded += 1` | 当日额度确认消耗 |
| 最终失败 | `reserved -= 1`，`released += 1` | 释放额度 |
| 用户取消 | `reserved -= 1`，`released += 1` | 仅在确认任务不会继续执行后释放 |
| 可恢复失败、重试中或状态未知 | 不变 | 继续占用，直至确定终态 |
| 最终超时 | `reserved -= 1`，`released += 1` | 必须先确认执行已经终止 |

结算以任务 ID 为幂等单位。重复回调、Worker 重启或消息重复消费只能完成一次状态迁移。批量任务逐项结算：成功项计入 `succeeded`，最终失败项计入 `released`；entry 中各项全部结束后再将 entry 标记为 `settled`。

跨日任务始终更新 `quota_business_date` 指向的原账本，不占用完成日额度。

## 9. 修改 `daily_quota` 的规则

新增管理员专用接口：

```http
PUT /api/admin/users/{user_id}/daily-quota
Content-Type: application/json

{ "daily_quota": 2000, "reason": "运营调整" }
```

规则如下：

- 只有管理员可以修改额度，普通用户不能通过个人资料接口修改自己的 `daily_quota`。
- 新值从修改成功后的新准入请求开始生效；修改发生时已经进入准入流程的请求使用其读取到的额度快照。
- 升额不会清除当日已有计数，用户可以使用增加后的剩余额度。
- 降额不会取消已接收任务。当 `occupied` 大于新值时，`remaining` 为 `0`，后续提交被拒绝，直到次日或占用因失败而释放。
- 修改操作记录管理员 ID、目标用户 ID、旧值、新值、原因和时间。
- 用户创建与更新模型为 `daily_quota` 增加非负整数校验；个人资料更新使用字段白名单。

## 10. 查询接口

新增当前用户额度查询接口：

```http
GET /api/analysis/quota
```

响应示例：

```json
{
  "limit": 1000,
  "reserved": 2,
  "succeeded": 5,
  "occupied": 7,
  "remaining": 993,
  "business_date": "2026-10-30",
  "resets_at": "2026-10-31T00:00:00+08:00"
}
```

没有当日账本文档时，计数均返回 `0`，`remaining` 等于 `users.daily_quota`。前端展示以该接口为准，不再使用 `this.user?.daily_quota || 1000` 推算剩余额度，避免合法值 `0` 被替换为 `1000`。

## 11. 故障和安全策略

- MongoDB 额度账本不可用、条件更新结果未知或用户额度非法时拒绝新提交并返回 `503`。
- Redis 可以缓存查询结果或承担请求频率限制，但不能作为额度事实来源。
- `user_id` 只能来自认证上下文，不能接受请求体传入的用户 ID。
- 客户端不能传入额度、已用量、业务日或结算状态。
- 管理员修改额度必须鉴权并写审计记录。
- 日额度不能替代接口频率限制和并发任务限制，三者分别防止不同类型的资源滥用。
- 额度预占、拒绝、释放、恢复失败和非法用户数据均记录结构化日志，日志中包含提交 ID、任务 ID、用户 ID、业务日和变化量。

## 12. 数据迁移和上线

上线前执行一次用户数据检查和迁移：

1. 统计 `daily_quota` 缺失、非整数和负数的用户，先输出异常清单。
2. 缺失字段按现有身份初始化：普通用户补 `1000`，管理员补 `10000`。
3. 非整数和负值必须按审核后的明确值修复，不在迁移脚本中猜测。
4. 为 `analysis_quota_daily` 创建唯一索引。
5. 部署额度服务、查询接口、管理员接口和任务恢复逻辑。
6. 将四个提交入口统一切换到额度服务。
7. 先以只记录不拒绝的观察模式核对请求成本和结算，再开启强制拒绝。观察模式只能控制是否拒绝，用户额度值仍从 `users.daily_quota` 读取。
8. 开启后监控 `DAILY_QUOTA_EXCEEDED`、MongoDB 准入失败、长期预占和计数不变量。

账本必须持续满足：

```text
reserved >= 0
succeeded >= 0
released >= 0
每个 entry 的 reserved + succeeded + released = cost
日账本汇总值 = 所有 entries 对应状态值之和
```

## 14. 测试与验收

至少覆盖以下场景：

- `daily_quota` 为 `0`、`1`、普通用户历史值 `1000` 和管理员历史值 `10000`。
- 单股成功、最终失败、取消、可恢复失败和确认超时。
- 批量代码规范化和去重，余额不足时整批拒绝，部分成功时逐项结算。
- 20 个并发请求争抢最后额度，成功预占总量不超过上限。
- 相同幂等键重复提交只占用一次；相同键对应不同参数返回 `409`。
- MongoDB 写入成功但响应超时后，使用原幂等键重试可以找回原结果。
- 任务持久化失败后可恢复或释放，不留下永久孤儿预占。
- 任务跨午夜完成时结算到首次预占日。
- 当日升额和降额后，已有占用不清零，降额不取消已接收任务。
- 四个分析提交入口共享同一账本，不能通过替换接口绕过。
- 普通用户不能修改自己的额度，管理员修改会产生审计记录。
- `user_tags` 的新增、修改和删除不影响额度。
- MongoDB 不可用或 `daily_quota` 非法时返回 `503`，不会放行分析。

验收标准是：任何并发和重试条件下，用户单个业务日的 `reserved + succeeded` 均不超过准入时读取的有效 `users.daily_quota`；所有终态任务均完成一次且仅一次结算；四个入口无法绕过统一准入。

## 15. 设计决策

采用 `users.daily_quota` 与 MongoDB 每日账本的组合。用户文档保存长期额度配置，每日账本保存高频占用和结算状态。该方案复用已有字段，能用单文档条件更新解决并发超额，并通过提交意图和固定任务 ID解决预占与任务创建之间的一致性问题。

本设计仅定义后续实现方案，当前未修改业务代码。
