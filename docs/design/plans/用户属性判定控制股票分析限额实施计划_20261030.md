# 用户属性判定控制股票分析限额实施计划

> 日期：2026-10-30
> 依据：[用户属性判定控制股票分析限额设计文档_20261030.md](../design/用户属性判定控制股票分析限额设计文档_20261030.md)
> 范围：`users.daily_quota` 日额度账本、四个分析提交入口统一准入、任务结算、幂等重试、管理员额度管理、前端配合
> 前置说明：本计划只排实施步骤和验收，不重新讨论已拍板的规则；规则冲突时以设计文档为准。

## 0. 目标与验收口径

- `users.daily_quota` 对全部四个分析提交入口（`/api/analysis/single`、`/api/analysis/batch`、`/api/analysis/analyze`、`/api/analysis/analyze/batch`）实际生效。
- 任一并发、重试、跨日条件下，单用户单业务日 `reserved + succeeded` 不超过准入时读取的额度。
- 每个终态任务恰好结算一次：成功计 `succeeded`，最终失败/取消/确认超时计 `released`。
- 相同幂等键重试不重复扣减；不同参数复用同一键返回 `409`。
- 普通用户无法通过任何接口修改自己的 `daily_quota`；管理员修改有审计记录。

## 1. 现状关键结论（排期依据）

- `POST /single` 走 `SimpleAnalysisService.create_analysis_task` + `BackgroundTasks` 直跑，`POST /batch` 走 `asyncio.create_task` 直跑，均不经过 `QueueService`。
- `POST /analyze`、`POST /analyze/batch` 走 `QueueService.enqueue_task` / `create_batch`，由 Worker 执行。
- 因此额度准入必须在路由/准入服务层统一完成，不能依赖队列层；本功能只承诺日额度，直跑路径的并发问题不在本期范围。
- `SimpleAnalysisService.create_analysis_task` 目前 MongoDB 写入失败后仅记录日志仍返回成功，接入额度前必须先修一致性问题。
- `UserUpdate` 模型当前包含 `daily_quota`/`concurrent_limit`，`UserService.update_user` 会直接落库；虽然 `PUT /api/auth/me` 做了字段白名单，仍需在模型与服务层收口，防止其他更新路径透传。
- 队列并发 `user_concurrent_limit`/`global_concurrent_limit` 目前都被系统配置 `max_concurrent_tasks` 覆盖，未读取 `users.concurrent_limit`，该问题列为独立后续项（见 8.2）。
- 现有管理员接口集中在 `app/routers/auth_db.py`（`/api/auth` 前缀），管理员额度接口落位于该路由，对外路径以实际注册前缀为准。

## 3. 详细执行步骤

### P0 数据体检与配置准备

1. 新增一次性脚本 `scripts/check_user_daily_quota.py`：
   - 统计 `users` 集合中 `daily_quota` 缺失、非整数、负数的用户，输出异常清单；
   - 缺失字段按身份补齐：普通用户 `1000`，`is_admin=true` 用户 `10000`；
   - 非整数/负值只输出清单，不在脚本内猜测修复值，由运营确认后人工修复。
2. 新增配置项（`app/core/config.py` / 系统设置）：
   - `QUOTA_MODE`：`disabled | observe | enforce`，默认 `disabled`；
   - `QUOTA_BUSINESS_TZ`：默认 `Asia/Shanghai`；
   - `QUOTA_RESERVED_TTL_MINUTES`：预占恢复扫描的超时阈值，默认 `30`。
3. 确认部署形态：MongoDB 是否为副本集（决定预占+任务写入是否可用事务）；不阻塞主流程，按无事务方案实现。

验收：脚本在测试库输出报告；配置项可读且有默认值。

### P1 每日账本模型与 `AnalysisQuotaService`

1. 新建 `app/models/quota.py`：账本与 entry 的 Pydantic 模型，字段对齐设计文档第 5 节。
2. 新建 `app/services/analysis_quota_service.py`，核心方法：
   - `business_date()`：按 `QUOTA_BUSINESS_TZ` 计算 `YYYY-MM-DD`；
   - `get_quota(user_id)`：读取 `users.daily_quota` 并校验为非负整数，非法抛 `QuotaConfigError`；
   - `reserve(user_id, normalized_items, idempotency_key, request_hash, task_ids)`：
     - 幂等键 SHA-256 生成提交 ID；同键同 `request_hash` 直接返回原 entry；
     - 同键不同 `request_hash` 返回冲突；
     - 在 `analysis_quota_daily` 上用条件原子更新（`$expr` 比较 `reserved + succeeded + cost <= 准入时额度`）写入 entry 并 `$inc` `reserved`；
     - 结果返回 `{submission_id, cost, limit, occupied, remaining, business_date}`。
   - `settle(task_id, outcome)`：按任务幂等迁移 entry 内单项状态，成功 `reserved-1/succeeded+1`，最终失败/取消/确认超时 `reserved-1/released+1`；重复调用返回已结算结果。
   - `get_status(user_id)`：返回 `limit/reserved/succeeded/occupied/remaining/business_date/resets_at`。
3. 建索引：应用启动或迁移脚本执行

   ```javascript
   db.analysis_quota_daily.createIndex(
     { user_id: 1, business_date: 1 },
     { unique: true, name: "uk_user_business_date" }
   )
   ```

4. 结构化日志：预占/拒绝/释放/冲突/非法额度，均带 `submission_id`、`user_id`、`business_date`、`cost`。
5. 单元测试 `tests/unit/test_analysis_quota_service.py`：余额边界（0/1/刚好满）、并发预占不超发、幂等重放、哈希冲突、非法额度。

验收：不开入口的情况下，直接调服务可完成预占→结算全链路；账本满足不变量 `entry.reserved + entry.succeeded + entry.released = entry.cost`。

### P2 任务创建一致性改造

1. `app/services/simple_analysis_service.py`：
   - `create_analysis_task` 增加可选参数 `task_id`、`quota_meta`；未传时保持原 UUID 行为；
   - MongoDB 初始文档写入失败时抛出异常，不再"记录错误但继续执行"；
   - 任务文档写入 `quota_submission_id`、`quota_business_date`、`quota_cost`（有额度元数据时）。
2. `app/services/queue_service.py`：
   - `enqueue_task`/`create_batch` 支持传入固定 `task_id` 与额度元数据；
   - 任务入队文档同样写入三个额度关联字段；
   - 重复任务 ID 投递去重（依赖 `task_id` 幂等 upsert）。
3. 保持 `AnalysisTask`/`analysis_tasks` 向后兼容：旧任务无额度字段时结算逻辑直接跳过。

验收：杀掉 MongoDB 后调用创建接口返回 5xx 而非"成功"；重复创建同一 `task_id` 不产生第二条文档。

### P3 终态结算与孤儿预占恢复

1. 在统一的任务终态出口接入 `AnalysisQuotaService.settle()`：
   - `SimpleAnalysisService.execute_analysis_background` 的 COMPLETED / FAILED 分支；
   - `AnalysisWorker` 完成处理（`queue_service` `completed/failed` 回写处）；
   - `POST /tasks/{task_id}/cancel` 与 `QueueService.cancel_task`（确认任务不会继续执行后才释放）；
   - `POST /tasks/{task_id}/mark-failed` 管理员接口；
   - 僵尸任务清理（`/admin/cleanup-zombie-tasks` 与 visibility timeout 回收路径）按"最终超时"结算。
2. 恢复逻辑（挂到现有 scheduler 或服务内定时协程）：
   - 扫描 `entries` 中 `status=reserved` 且超过 `QUOTA_RESERVED_TTL_MINUTES` 未更新的项；
   - 任务文档存在：按任务当前状态补结算；
   - 任务文档不存在且可重建：按 entry 恢复创建并投递；
   - 不可重建且确认未执行：幂等释放；
   - 状态不明：保留预占并告警，不放行。
3. 跨日：结算一律写回 `quota_business_date` 指定的账本，不占用完成日额度。

验收：构造 ①正常成功 ②执行异常 ③取消 ④标记失败 ⑤超时回收 ⑥预占后进程崩溃六种任务，账本均完成恰好一次结算。

### P4 四个入口统一准入与幂等

1. `app/routers/analysis.py` 四个 POST 入口在参数校验后、任务创建前统一调用 `reserve()`：
   - 规范化市场/股票代码、批量去重（复用 `BatchAnalysisRequest.get_symbols()` 与既有规范化逻辑）后计算 `cost`；
   - 服务端预生成固定 `task_id` 列表并随请求传给创建/入队方法；
   - `Idempotency-Key` 从 Header 读取，缺失或非法返回 `400`；
   - 异常映射：额度不足 → `429` + `DAILY_QUOTA_EXCEEDED` 结构体；键冲突 → `409`；写入结果未知 → `503`；
   - 预占成功后任一步骤失败且不可恢复时，执行幂等释放再返回错误。
2. `observe` 模式：照常写账本与日志，超额时记 `would_reject` 并放行；`enforce` 模式才真正拒绝；`disabled` 不接入。
3. 新增 `GET /api/analysis/quota`：返回 `get_status()` 结果，路由落位于 `analysis.py`。
4. 批量整批语义：余额不足整批拒绝，不产生部分任务；`MAX_BATCH_SIZE=10` 现有约束保留。

验收：四个入口共享同一账本；余额不足时四个入口返回一致的 `429` 结构；重放同键请求返回原 `task_id` 且不重复计数。

### P5 用户模型收口、管理员接口与审计

1. `app/models/user.py`：`User.daily_quota` 加 `ge=0` 校验；`UserUpdate` 移除 `daily_quota`/`concurrent_limit`（或改为独立 `AdminUserUpdate`），普通用户更新路径不再可写额度字段。
2. `app/services/user_service.py`：`update_user` 去掉两个额度字段的落库分支；新增 `update_daily_quota(admin_id, user_id, new_value, reason)`，校验非负整数并写审计。
3. `app/routers/auth_db.py`：新增 `PUT /users/{user_id}/daily-quota`，仅 `is_admin`；请求体 `{daily_quota, reason}`。
4. 审计：优先复用 `app/services/operation_log_service.py`；记录管理员 ID、目标用户、旧值、新值、原因、时间。
5. 升/降额语义按设计文档第 9 节：不清已有计数，降额不取消已收任务。

验收：普通用户经 `PUT /me`、资料接口、直接构造 `UserUpdate` 均无法改动 `daily_quota`；管理员修改后新准入请求立即使用新值且可查审计。

### P6 前端配合

1. `frontend/src/api/analysis.ts`：
   - 单股/批量提交前生成 `crypto.randomUUID()` 作为 `Idempotency-Key`；
   - 进行中请求的键持久到内存 store（刷新前）并在未知结果重试时复用；
   - 新增 `getQuota()` 调 `GET /api/analysis/quota`。
2. `frontend/src/stores/auth.ts`：把 `daily_quota || 1000` 类写法改为 `??`，确保合法的 `0` 不被覆盖；页面展示剩余额度以 `/quota` 接口为准。
3. 提交页面与全局拦截：识别 `429`/`DAILY_QUOTA_EXCEEDED`，提示当日额度与重置时间 `resets_at`。
4. 管理页：用户列表增加额度展示与编辑入口（调 P5 接口），编辑需填原因。
5. `cd frontend && npm run type-check && npm run lint` 通过。

### P7 观察模式 → 强制上线

1. 灰度顺序：`disabled`（功能代码上线不启用）→ `observe`（至少覆盖 1 个完整业务日）→ `enforce`。
2. 观察期核对：
   - 不变量巡检脚本：`reserved/succeeded/released >= 0`，entry 三项之和等于 `cost`；
   - `would_reject` 日志量级评估真实影响面；
   - 与历史同日提交量对比 `cost` 统计是否合理（验证批量规范化/去重正确性）。
3. `enforce` 开启后监控：`DAILY_QUOTA_EXCEEDED` 次数、MongoDB 准入 5xx、长期 `reserved` entry 数、结算延迟。
4. 回滚预案：配置切回 `observe`/`disabled` 即恢复旧行为；账本数据保留不影响既有任务。

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 预占成功但任务未落库 | 额度被占不放 | 固定 task_id + entry 恢复扫描（P3.2） |
| 直跑路径（`/single`、`/batch`）不经队列 | 并发不受 `concurrent_limit` 约束 | 本期仅保证日额度；并发收口列入 8.2 后续项 |
| `entries` 内嵌数组过大 | 单文档逼近 16MB | 批量上限 10 + 提交频率限制；超限再拆独立集合（设计已预留方案） |
| 兼容端点无幂等键历史调用 | 上线后 400 | 前端先行发版带键；observe 期对缺键请求只记告警，enforce 再拒绝 |
| `UserUpdate` 收口破坏既有管理功能 | 管理员原有编辑链路报错 | 先盘点全部 `update_user` 调用方（`auth_db.py` 三处），改用 `AdminUserUpdate` |
