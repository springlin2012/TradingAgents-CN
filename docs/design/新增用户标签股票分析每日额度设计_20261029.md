# 用户标签股票分析每日额度设计

> 日期：2026-10-29  
> 状态：设计草案，待评审；本次未修改业务代码。  
> 已明确需求：首席体验官默认每天 10 次、普通用户默认每天 2 次，次数可配置；admin 管理员不受每日次数限制。  
> 已确认计次口径：分析中任务占用次数，分析成功任务消耗次数；分析失败、取消或确认最终超时后释放次数。

## 一、业务规则

| 用户身份 | 默认每日额度 | 配置方式 |
| --- | ---: | --- |
| 管理员（数据库 `is_admin=true`，包含 admin 账号） | 不限 | 固定豁免，不受标签额度和默认额度影响 |
| 首席体验官 | 10 次 | 管理员修改身份标签的每日分析次数 |
| 普通用户、没有身份标签的用户 | 2 次 | 管理员修改默认每日分析次数 |

1. 使用北京时间 `Asia/Shanghai`，每日 00:00 开始新一天；周末和节假日同样计算，不按最近 24 小时滚动统计。
2. 每只股票需要 1 次额度。任务进入分析中、排队或可恢复状态时占用 1 次；分析成功后转为成功消耗；最终失败、取消或确认最终超时后释放。分析深度、分析师数量、内部模型调用和工具重试不影响次数。A 股、港股、美股共用账号额度。
3. 批量按股票数量占用额度。先规范化市场和代码、去除同一批内重复股票，再计算数量。整批准入时原子占用全部额度，执行后按每只股票分别结算。例如批量分析 3 只，2 只成功、1 只失败，最终只消耗 2 次。保留现有单批最多 10 只的技术限制。
4. 批量额度不足时整批拒绝，不创建任何可执行任务，也不占用部分次数。例如剩余 2 次提交 3 只，提示减少到 2 只后重新提交。
5. 参数校验失败、身份校验失败、额度不足不占用次数；同一个提交的网络重试、内部重试和恢复不重复占用。使用新的提交标识重新分析同一股票属于新任务，需要重新占用。
6. 状态未知、仍可恢复或外部 LLM 调用结果未知时继续占用，不提前释放。读取历史报告、刷新进度、下载报告和浏览行情不计次。
7. 用户具有多个身份标签时，取匹配标签额度的最大值；没有匹配到启用的额度规则时使用普通用户默认额度。普通用户默认额度仅作为兜底，不参与最大值计算。
8. 标签额度允许配置为 0，表示该标签本身不提供可用次数；多个标签仍按最大值合并。若要禁用账号，应使用现有 `is_active`，不依赖标签额度。
9. 标签、默认额度及身份变更对变更成功后的新提交生效；已有分析中任务沿用首次占用时的规则快照。当日占用量按 `succeeded + reserved` 计算。例如从普通用户升级为体验官且当日占用 2 次，则剩余 8 次；降为普通用户且当日占用 5 次，则剩余 0 次。
10. 管理员升降级不回改历史计数：豁免期间的任务不进入额度账本，降级后以当日已有的非豁免占用量继续判断。管理员豁免每日次数，不豁免身份校验、参数校验和系统资源保护。

## 三、方案比较与推荐

| 方案 | 优点 | 代价或限制 |
| --- | --- | --- |
| **身份标签规则 + MongoDB 原子准入，推荐** | 规则与用量持久化；单文档更新控制并发；可兼容当前单机 MongoDB | 需要设计幂等记录和任务恢复，避免计数与任务分属两次写入造成遗漏 |
| 身份标签规则 + Redis Lua 计数 | 高并发开销低，可一次完成检查和占用 | Redis 丢失计数可能恢复出额外额度；持久审计与缓存间仍需一致性处理 |
| 每次从分析任务表统计今日任务数 | 初期代码少 | “先统计、再建任务”存在并发超额；现有任务状态、用户标识和历史数据也不适合作为额度账本 |

本需求默认每天 2～10 次，推荐以 MongoDB 为唯一额度事实来源。Redis 继续承担现有队列和进度职责，不保存第二套权威额度。使用单文档原子更新，不要求为了本功能把现有 MongoDB 改为副本集。

## 四、身份标签和配置

### 4.1 身份标签

新增管理员维护的 `account_labels` 集合，与现有 `user_tags` 隔离。

| 字段 | 含义 |
| --- | --- |
| `_id` | 稳定标签标识，用户关联和规则匹配均用此值 |
| `code` | 唯一业务编码，例如 `chief_experience_officer` |
| `name` | 中文名称，例如“首席体验官” |
| `enabled` | 是否启用该身份标签 |
| `daily_analysis_limit` | 每日次数，整数 0～10000；不允许负数表示无限 |
| `version`、`updated_at`、`updated_by` | 版本与变更审计 |

用户新增 `account_label_ids: []`。普通用户默认不需要关联标签；界面显示“普通用户”。只有管理员能赋予、移除身份标签。标签改名不影响关联；删除已被引用的标签返回 409，管理员可先停用或移除关联。

### 4.2 全局配置

新增专用 `analysis_quota_settings` 配置文档，固定 `_id=default`：

| 字段 | 初始值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 功能总开关，关闭时允许提交且不新增额度计数；保留历史用量 |
| `default_daily_limit` | `2` | 普通用户默认额度，整数 0～10000 |
| `timezone` | `Asia/Shanghai` | 首期固定，只读显示，避免日内改时区导致重复窗口 |
| `version` | `1` | 更新时递增，并用于并发编辑校验 |
| `updated_at`、`updated_by` | 初始化时间和执行人 | 审计信息 |

初始化“首席体验官”标签，额度为 10。初始化采用仅不存在时插入，不覆盖管理员已有配置，也不自动把任何用户升级为体验官。

配置和标签规则首期直接读取 MongoDB，不使用进程内长缓存。每次提交读取一份规则快照，记录有效额度、规则来源及版本。配置更新完成后的新提交使用新规则；已开始准入的请求按自身快照完成，不撤销已经接收的任务。

规则解析顺序：认证及账号启用校验 → `is_admin` 豁免 → 总开关 → 有效身份标签最大额度 → 普通用户默认额度。

### 4.3 旧配额字段处理

旧 `users.daily_quota` 不再参与新额度判断，不提供个人覆盖规则，防止历史 1000/10000 优先于标签配置。新接口返回统一的 `effective_daily_limit`、`unlimited` 和 `remaining`。排查并替换前端的 `|| 1000` 兜底，确保额度 0 能正确显示。

历史字段暂保留以兼容数据结构，明确标记废弃。仍需兼容的旧响应字段应映射为有效额度：有限用户返回整数，无限用户返回 `null` 并同时提供 `unlimited=true`；对应响应模型和客户端类型同步允许 `null`。不以 999999 等任意大数表示无限。

## 五、统一准入与计数

### 5.1 服务职责

- `AnalysisQuotaService`：解析规则、查询用量、原子预占额度，并按任务结果完成成功或释放结算。
- `AnalysisSubmissionService`：校验和规范化请求、管理幂等提交、生成任务意图、调用额度服务、投递任务。
- 管理接口：维护默认额度、身份标签和用户关联，统一校验管理员权限并记录操作日志。

四个 HTTP 提交入口只组装请求后调用统一提交服务；简化服务和队列服务只执行已经准入的任务。批量内部调用创建单股任务时传递接收凭据，不再次占用额度。队列消费和后台恢复也不再次占用额度。

### 5.2 数据结构

**每日账本 `analysis_quota_daily`**：唯一键 `(user_id, business_date)`。

| 字段 | 含义 |
| --- | --- |
| `user_id` | 当前认证用户的规范字符串 ID，禁止来源不明的随机 ID 替代 |
| `business_date` | 北京日期，例如 `2026-10-29` |
| `reserved` | 分析中、排队或仍可恢复的任务数量 |
| `succeeded` | 当日分析成功并正式消耗额度的任务数量 |
| `entries` | 以 `task_id` 为键保存精简额度条目，包含状态、提交标识、规则快照和时间；不内嵌大参数或报告 |
| `created_at`、`updated_at`、`expire_at` | UTC 时间；全部关联任务终结后才设置清理时间 |

`occupied = reserved + succeeded`，`remaining = max(effective_daily_limit - occupied, 0)`。额度条目有以下状态：

| 状态 | 含义 | 后续转换 |
| --- | --- | --- |
| `reserved` | 已占用，任务正在分析、排队或仍可恢复 | 可转为 `succeeded` 或 `released` |
| `succeeded` | 已成功消耗 | 终态 |
| `released` | 最终失败、取消或最终超时后已释放 | 终态 |

状态转换必须在同一账本文档内原子且幂等：无记录转 `reserved` 时 `reserved += 1`；`reserved` 转 `succeeded` 时 `reserved -= 1`、`succeeded += 1`；`reserved` 转 `released` 时 `reserved -= 1`。重复成功或失败回调不改变计数，`succeeded` 不回退，`released` 不允许旧执行实例转为成功。批量准入时在同一用户当日账本内一次写入 N 个 `reserved` 条目，条件为 `reserved + succeeded + cost <= effective_daily_limit`。

首次通过唯一键和 `$setOnInsert` 创建 `reserved=0`、`succeeded=0` 的账本，处理并发初始化的重复键后再执行条件更新；额度占用阶段禁止条件不匹配时 `upsert` 新文档。

**提交记录 `analysis_submissions`**：唯一键 `(user_id, idempotency_key)`，用于任务意图持久化及跨日期重试定位。

保存请求摘要、固定的 `business_date`、原始规范化参数、预生成的 `task_ids`/`batch_id`、消耗数量、规则快照、豁免原因、状态及时间。状态包括 `preparing`、`accepted`、`rejected`。执行投递情况使用独立状态，不修改接收结果。状态变更使用条件更新，恢复进程和 HTTP 请求通过租约避免同时推进同一提交。

提交记录保留至少 90 天，且在有关任务未完成或接收状态尚未收敛时不清理。账本存在 `reserved` 条目或关联任务尚未终结时不得设置过期时间；全部条目终结并完成一致性检查后再设置 TTL 清理时间。TTL 不是每日重置机制。

每日额度上限 10000 既满足当前需求，也限制每日账本条目规模；任务和提交标识必须为规范 UUID，账本仅内嵌精简计数元数据。实现前必须按 10000 个条目做 BSON 体积测试，确保明显低于 MongoDB 16 MiB 文档限制。若实际超限，应降低配置上限，或在 MongoDB 事务可用时拆分计数与条目；不能使用无事务的双集合写入破坏原子性。满额拒绝记录不写入每日账本。

### 5.3 接收流程

1. 校验认证用户、有效账号、股票代码、分析参数和单批规模；完成规范化及批内去重，得到本次所需次数 `cost`。
2. 查询幂等键。已有提交且请求摘要相同则继续原状态或返回原任务；摘要不同返回 409。查重先于重新判断额度，已接收提交不会因后来额度降低而变成拒绝。
3. 新提交先持久保存 `preparing` 记录和完整任务意图，固定北京业务日期及任务 ID；并发相同键仅一个写入成功。用户 ID、幂等键和请求摘要共同约束重复行为。
4. 读取身份和规则，将快照写入提交记录后再准入；恢复时复用已经保存的快照，不因重试切换规则。管理员或总开关关闭时记录豁免原因，不进入额度账本。
5. 有限用户执行**一次单文档原子更新**：条件为任务尚未记账且 `reserved + succeeded + cost <= 本次有效额度`；同次更新增加 `reserved` 并为全部任务写入 `reserved` 条目。不同股票或不同接口对同一用户同一天共享此条件。
6. 条件未匹配时先检查这些任务是否已经预占：已预占则按成功恢复；未预占且额度不足则转为 `rejected` 并返回 429。数据库超时属于结果未知，返回 503；客户端必须使用原幂等键重试，不能直接当作额度不足或重新占用。
7. 预占成功后将提交状态转为 `accepted`，再按固定任务 ID 物化和投递任务。如在两次写入之间崩溃，恢复进程根据账本条目补齐状态，再继续创建任务。
8. 只为已接收的提交按固定任务 ID 物化任务记录并投递。返回原有任务信息及最新额度；任务暂时无法投递时仍返回已接收和等待执行，交给恢复流程继续。

额度计数与任务条目在同一文档原子变更，避免并发超额。任务意图在预占前已经持久化，避免“占了次数但没有任何可恢复请求”。任务记录按 `task_id` 唯一并幂等创建，投递使用提交租约及任务执行状态校验，避免 HTTP 重试或恢复扫描重复启动同一分析。领取任务时使用原子状态迁移和执行令牌；旧执行实例丢失所有权后禁止继续推进或落结果。

首期恢复进程扫描 `preparing` 和未完成投递的 `accepted` 记录：已预占的补齐接收状态；未预占的继续原子准入或明确拒绝；已接收的补齐任务并投递。恢复操作不生成新任务 ID。外部 LLM 在网络结果未知时仍可能发生重复调用，额度层保证同一任务只占用一次，不承诺外部调用恰好一次。

### 5.4 任务结算流程

1. 成功路径在业务任务先持久化为成功终态后调用 `settle_success(task_id)`；最终失败、取消或确认最终超时路径在业务任务先持久化为对应终态后调用 `settle_release(task_id, reason)`。
2. 结算使用任务首次占用时保存的 `business_date` 定位原账本，即使任务跨日完成也不移动到新一天。所有执行器统一调用额度服务，不能自行加减计数。
3. 更新条件必须匹配 `entries.<task_id>.status=reserved`。条件不匹配时读取当前状态：与目标状态相同视为幂等成功；若已处于另一终态，则记录一致性告警且不改变计数。
4. 业务任务终态与额度条目分属两个 MongoDB 文档，无法依赖普通单文档写入保证同时成功。恢复任务定期扫描不一致状态并按固定规则收敛：成功任务补为 `succeeded`，最终失败或取消任务补为 `released`，仍运行或仍可恢复的任务保持 `reserved`。
5. `released` 后不允许迟到结果把业务任务或额度条目“复活”为成功。执行器必须持有有效租约或执行令牌，丢失所有权后不得写入结果。

### 5.5 关键边界

- **并发**：普通用户同时提交 20 个不同单股请求，最多 `occupied=2`；其余返回额度不足。
- **批量**：先保存一个整批意图，再一次占用全部次数；额度不足不得留下可执行子任务。准入后按每只股票独立结算，部分任务物化失败由恢复补齐。
- **跨日**：首次占用固定日期。23:59 开始、次日成功仍结算前一天的成功次数；次日失败则释放前一天的占用。次日新提交使用新账本，不受前一天仍在运行的任务影响。跨午夜使用同一幂等键返回前一天的原任务。
- **重置**：第二天访问新的日期账本，自然获得新额度，不运行“统一清零”任务。
- **故障**：MongoDB 无法读取权威身份、规则或额度时返回 503，不按普通用户 2 次静默回退，也不放行未确认额度的新任务。Redis 故障不改变账本，已接收的队列任务等待恢复。
- **用户取消**：业务任务确认进入 `cancelled` 终态后释放；取消请求已发出但执行器尚未确认时继续占用。
- **超时**：HTTP 请求超时不释放。只有任务达到最终超时、确认执行租约失效，并先写入最终失败状态后才释放。客户端使用原幂等键重试。
- **僵尸任务**：不能仅因短暂心跳丢失释放；任务仍可恢复时继续占用。恢复器在确认执行租约失效且任务达到最终失败条件后释放。
- **迟到结果**：额度条目一旦 `released`，旧执行实例的迟到结果不得写为成功，以免突破当日上限。

## 六、接口设计

以下均为拟新增或拟调整契约，不代表接口已经实现。成功响应复用 `app/core/response.py:ok` 格式。

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/analysis/quota` | 当前用户 | 查询自己的有效额度、分析中、成功、占用、剩余、命中标签和重置时间 |
| `GET /api/admin/analysis-quota/settings` | 管理员 | 查看配额全局配置 |
| `PUT /api/admin/analysis-quota/settings` | 管理员 | 修改开关和普通用户默认额度，携带预期版本 |
| `GET /api/admin/account-labels` | 管理员 | 身份标签列表及对应额度 |
| `POST /api/admin/account-labels` | 管理员 | 创建身份标签 |
| `PUT /api/admin/account-labels/{label_id}` | 管理员 | 修改名称、额度、启用状态，携带预期版本 |
| `DELETE /api/admin/account-labels/{label_id}` | 管理员 | 删除未被引用的身份标签 |
| `PUT /api/admin/users/{user_id}/account-labels` | 管理员 | 替换用户身份标签关联，校验全部标签存在 |
| `GET /api/admin/users/{user_id}/analysis-quota` | 管理员 | 查看某用户当前额度及当日用量 |

普通用户额度响应的数据部分示例：

```json
{
  "unlimited": false,
  "effective_daily_limit": 10,
  "in_progress": 1,
  "succeeded": 2,
  "occupied": 3,
  "remaining": 7,
  "labels": [{"id": "标签标识", "name": "首席体验官"}],
  "rule_source": "account_label",
  "business_date": "2026-10-29",
  "timezone": "Asia/Shanghai",
  "resets_at": "2026-10-30T00:00:00+08:00"
}
```

管理员返回 `unlimited=true`、`effective_daily_limit=null`、`remaining=null`、`rule_source=admin`。`in_progress`、`succeeded` 和 `occupied` 可返回 0，或仅表示当日非豁免账本数据；契约必须明确管理员豁免期间的任务不计入这些数字。开关关闭时来源为 `disabled`，同样显示无限。

四个提交端点均支持 `Idempotency-Key` 请求头。Vue 在一次用户点击时生成 UUID，超时重试复用；主动再次分析生成新 UUID。兼容调用方过渡期缺少此头时由服务端生成并回传，但响应丢失后无法保证调用方的新请求被识别为同一次提交；升级后的正式客户端应始终传递该头。

错误约定：

| 状态 | 业务码 | 行为 |
| --- | --- | --- |
| 429 | `ANALYSIS_DAILY_QUOTA_EXCEEDED` | 返回 `in_progress`、`succeeded`、`occupied`、`remaining`、`required` 和 `resets_at`，设置 `Retry-After` 为到下一次北京时间零点的秒数 |
| 403 | `ADMIN_REQUIRED` | 普通用户尝试修改额度或账号标签 |
| 409 | `IDEMPOTENCY_KEY_CONFLICT` / `CONFIG_VERSION_CONFLICT` | 同一键不同参数，或配置已被其他管理员更新 |
| 503 | `ANALYSIS_QUOTA_UNAVAILABLE` | 不能确定准入结果，提示使用原幂等键重试 |

错误业务数据放入 FastAPI `HTTPException.detail`，统一包含 `code`、中文 `message` 和相关额度字段；前端读取 `response.data.detail`。四个提交路由需先 `except HTTPException: raise`，再处理其他异常，避免现有宽泛捕获把 429/503 改成 400。

## 七、界面交互

### 用户侧

- 单股、批量分析页显示“今日剩余 7 / 10 次，其中 1 次分析中（北京时间 00:00 恢复）”；管理员显示“管理员 · 分析次数不限”。
- 批量输入后显示“本次将占用 3 次”；剩余不足时提示减少数量。前端只作提示，最终以服务端原子准入为准。
- 提交成功后更新额度；任务失败并释放后自动刷新。页面进入、重新获得焦点和收到 429 时重新查询。多设备之间无需依靠前端同步保障限制。
- 429 文案：“今日分析次数不足：剩余 2 次，本次需要 3 次。请减少股票数量，或在北京时间明日 00:00 后再试。”
- 不向用户暴露个人分类标签与账号身份标签的存储差别；身份标签由账号信息展示，用户不能自行申请写入。

### 管理员侧

在系统管理增加“分析次数配置”和“用户身份标签”入口：

1. 修改默认每日次数、功能开关，查看固定的北京时间规则。
2. 标签列表维护名称、每日次数和启用状态；首席体验官预置为 10。
3. 用户管理支持分配身份标签，展示有效额度及今日分析中、成功、占用和剩余；管理员行固定显示“不限”。当前仓库具备用户查询接口，但完整标签分配页面需要新增。
4. 降低额度时提示“今日分析中与成功次数不会清零；当前占用超过新额度的用户今日无法继续提交”。变更记录操作人、对象、变更前后值及时间。

## 九、验收清单

| 场景 | 预期 |
| --- | --- |
| 普通用户连续提交 3 次 | 前 2 次处于分析中或成功时，第 3 次返回 429 |
| 普通用户前 2 次中有 1 次最终失败 | 失败任务释放后，第 3 次可以提交 |
| 成功任务 | 从 `reserved` 转为 `succeeded`，当日仍占用额度 |
| 体验官连续提交 11 次 | 前 10 次处于分析中或成功时，第 11 次返回 429 |
| 管理员执行超过 10 次且带 0 次标签 | 不受每日次数限制；仍校验参数 |
| 额度改为普通 3 次、体验官 20 次 | 变更后的新请求使用新额度，无需重启；当日分析中和成功次数保留 |
| 多身份标签额度 5、10 | 有效额度 10，不相加；普通用户默认值不参与比较 |
| 单个有效标签额度 0；标签停用 | 前者禁止新提交，后者忽略该标签并重新计算其他规则 |
| 剩余 2 次批量提交 3 只 | 整批拒绝，用量不变，无可执行子任务 |
| 单批内重复股票及不同市场同名代码 | 同一市场同一股票去重，不同市场分别计数 |
| 普通用户 20 个并发提交 | 最多接收 2 个，账本不超额 |
| 新旧四个接口混合提交 | 共用一个用户每日额度 |
| 相同幂等键并发或网络重试 | 同一组任务 ID、只占用一次；不同参数返回 409 |
| 预占成功后进程退出 | 恢复补齐接收状态和任务，不丢任务意图、不二次占用 |
| 批量 3 只，2 成功、1 最终失败 | 最终 `succeeded=2`、`reserved=0`，失败任务释放 1 次 |
| 重复成功或失败回调 | 计数不变；`succeeded` 后的失败回调不回退 |
| 已释放任务收到迟到成功结果 | 拒绝迟到结果，`released` 不转为 `succeeded` |
| HTTP 超时但任务仍运行 | 继续占用，不因客户端超时释放 |
| 任务最终超时且执行租约确认失效 | 先写最终失败状态，再释放占用 |
| 北京时间 23:59 开始、次日成功或失败 | 成功或释放均结算前一天账本；次日新请求使用新额度 |
| 业务终态与额度状态不一致 | 恢复扫描按固定规则补齐结算，不重复增减计数 |
| 普通升级体验官、标签降级、管理员降级 | 不清零历史计数，按新身份和现有用量计算剩余 |
| MongoDB 异常、写入超时、Redis 重启 | 额度状态未知时 503；原键重试可收敛；Redis 不重置额度 |
| 用户伪造标签、`is_admin` 或旧 `daily_quota` | 无法提升权限；个人分类标签不影响额度 |
| 并发管理员修改规则 | 版本冲突返回 409，变更可审计 |

实现时运行有针对性的后端单元测试及真实 MongoDB 并发/故障恢复测试；不能只用内存模拟证明原子性。前端变更运行 `npm run type-check`、`npm run lint`、`npm run build`，并检查普通用户、体验官、管理员及额度耗尽的显示。本次仅交付设计，未执行上述业务测试。
